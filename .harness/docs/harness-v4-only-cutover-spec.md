# Harness V4-Only Runtime Cutover Specification

Status: approved for incremental implementation; external formal authority remains fail-closed
Contract: `harness-v4-only-runtime-v1.0.0`
Engine release target: `4.0.0`
Date: 2026-07-30

## 1. Objective

Make Harness V4 the repository's only active planning, execution, aggregation,
audit and delivery-proof implementation. Remove V3 runtime behavior instead of
leaving a second compatibility implementation behind.

This cutover changes installed code authority. It does not fabricate missing
GitHub evidence. Protected merge or release remains blocked until the existing
H8 observation-window and external-enforcement requirements are independently
satisfied for the V4-only contract.

## 2. Approved decisions

1. `harness/version.json` identifies the installed engine as `4.0.0`.
2. V4 `outcome` values are the sole validation and process-decision authority.
   Active code must not upgrade or normalize a V3 status-only result.
3. The V3 historical projection adapter and every active caller are removed.
   Formal policy contains no V3 compatibility branch.
4. Historical V3 documents and sealed reports remain immutable audit evidence.
   They are not executable inputs, migration sources, fallback decisions or
   current-contract authorities.
5. H8 remains a V4 qualification mode. Its baseline suite, cold run, cached
   run, independent audit and adversarial corpus all execute the installed V4
   trust root after cutover; none invokes or adapts a V3 engine.
6. Existing sealed H8 observations remain immutable evidence. A trust-root
   change qualifies only when a post-cutover observation executes the
   protected adversarial corpus successfully.
7. Rollback pauses protected delivery or returns V4 development feedback. It
   cannot restore a V3 reader, writer, adapter, adjudicator or status upgrade.
8. Missing H8 qualification, external GitHub enforcement or an accepted formal
   run remains `BLOCKED`; no report or workflow may relabel it as formal PASS.

## 3. Active versus historical boundary

### 3.1 Active V4 surface

The active surface includes:

- `harness/cli.mjs`;
- `harness/lib/v4/**`;
- the V4 Validator, Safe Executor and independent Auditor;
- `harness/contracts/v4/**`;
- V4 qualification runners;
- V4 GitHub Actions workflows; and
- current V4 tests and operator documents.

Every active decision consumes an explicit closed V4 outcome. V3 status-only
records are rejected at the active boundary.

### 3.2 Historical evidence

The following may remain only as non-executable history:

- versioned V1-V3 hardening documents;
- completed H0-H9 reports that describe earlier migration observations;
- sealed GitHub Action observations created under superseded contracts; and
- Git history and release tags.

Historical artifacts must not be imported by runtime code, listed as current
policy sources, used to satisfy current acceptance, or mutated to imply they
were generated by V4-only code.

## 4. Runtime outcome contract

The closed check outcomes are:

```text
PASS
FAIL
BLOCKED
ERROR
CANCELED
NOT_APPLICABLE
```

The closed aggregate outcomes are:

```text
PASS
FAIL
BLOCKED
ERROR
CANCELED
INVALIDATED
```

Required observations must carry a valid `outcome`. A record that contains
only `status=passed`, `status=passed-or-skipped`, `status=skipped` or another
V3 status is contract-invalid and aggregates to `BLOCKED`, never PASS.

Lowercase lifecycle labels may remain only where they describe mutable process
state, such as a run being planned or a repair loop being active. They cannot
decide validation success, audit acceptance, CLI exit success, commit
permission, protected delivery or formal eligibility.

## 5. H8 V4 qualification

H8 remains installed because it is a V4 evidence-qualification subsystem, not
a V3 compatibility implementation. After the engine identity changes to
`4.0.0`:

- the baseline suite executes the V4 test and hook contract;
- the cold and cached executions use the V4 planner, Safe Executor, outcome
  engine and independent Auditor;
- the protected-base Judge remains separate from the candidate;
- cold/cached plan and decision digests must match;
- complete required-profile coverage remains mandatory; and
- every trust-root change must pass the protected adversarial corpus.

The term `baseline` describes a V4 control observation. It does not authorize a
status-only result and does not invoke the removed V3 adapter. Existing
observations retain their sealed identity; only observations satisfying the
current policy and trust-root rules may contribute to H9.

## 6. Formal policy

The formal cutover policy receives a new contract version. Its exact closed
shape contains no `legacyV3` object. The independent Auditor rejects an
unexpected V3/legacy compatibility field as a policy-shape violation.

Formal delivery still requires:

- a fresh `FORMAL_PASS` issued only by the independent Auditor;
- exact candidate commit/tree equality;
- a qualified V4-only H8 observation set;
- externally observed GitHub branch/ruleset enforcement; and
- an accepted formal workflow run for the delivered tree.

Removing V3 cannot weaken these requirements.

## 7. Migration slices

### Slice A — Red contract tests

Add focused tests that fail while any of these remain:

- engine identity below `4.0.0`;
- active `legacy-v3-adapter` source or import;
- status-only result normalization;
- formal-policy V3 compatibility field;
- H8 baseline execution or baseline observation field; or
- commit permission accepting `passed-or-skipped`.

### Slice B — Runtime authority

Promote engine identity, require explicit V4 outcomes at aggregation and use
outcomes for Validator, closeout, repair, CLI and hook decisions.

### Slice C — Formal policy and Auditor

Remove the adapter, remove V3 policy branches, version the policy contract and
prove unknown legacy fields fail closed.

### Slice D — H8 regression

Prove that H8 invokes only the promoted V4 runtime, that cold/cached
reproducibility and independent audit still pass, and that no V3 adapter or
status upgrade is reachable from the qualification runner.

### Slice E — Documentation and closeout

Update current runbooks and observation-derived current reports without
rewriting historical reports. Run focused tests, the full Harness test suite,
all plan-required profiles, Guard, post-validation Guard and independent
Auditor.

## 8. Acceptance

V4-only code acceptance requires all of the following:

1. `node harness/cli.mjs version` reports `4.0.0`.
2. No active source imports or implements a V3 adapter or V3 adjudicator.
3. Status-only V3 validation evidence is blocked by a focused negative test.
4. The commit hook does not accept `passed-or-skipped`.
5. Formal policy rejects any injected `legacyV3` field.
6. H8 baseline, cold and cached observations all execute V4-only sources.
7. Cold/cached V4 plans and decisions must match.
8. The full Harness regression suite passes.
9. The isolated migration closeout passes initial Guard, required validation,
   post-validation Guard and independent audit.
10. Current reports truthfully distinguish installed V4-only code from
    externally blocked formal authority.

The code-installation marker is:

```text
HARNESS_V4_ONLY_RUNTIME: PASS
```

The external formal marker remains:

```text
HARNESS_V4_FORMAL_CUTOVER: BLOCKED
```

until every external prerequisite is observed. The two markers are deliberately
different and cannot be substituted for one another.

## 9. Rollback and recovery

Before deleting active V3 code, retain the last V3 commit/tag as the recovery
point. Rollback is performed by reverting the V4-only migration commit, not by
shipping dormant V3 branches inside the current runtime.

If V4-only validation fails after installation:

1. stop protected delivery;
2. preserve all V4 evidence and failure diagnostics;
3. repair forward within the V4 contract; or
4. revert the entire cutover commit as one versioned change.

Partial rollback, status reinterpretation and selective restoration of V3
adjudication are prohibited.
